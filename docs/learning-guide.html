1. Text cleaning & stopwords

What it is

Text cleaning is the process of turning messy human language into a consistent string of useful tokens before any numerical conversion. Stopwords are extremely common words (the, is, of, and, …) that usually carry little topic signal for bag-of-words models.

Why we need it

  • Raw text has inconsistent casing, punctuation, symbols, and filler words.
  • Models like TF-IDF count tokens. Noise tokens waste vocabulary slots and dilute signal.
  • Cleaning makes “Music Album!” and “music album” look the same to the model.

How it works (typical pipeline)

  1. Lowercase — unify Music / music.
  2. Remove non-letters (or keep digits if your domain needs them).
  3. Tokenize — split into words.
  4. Drop stopwords — remove low-value common words.
  5. Optional: stemming/lemmatization, rare-word filtering (often done inside the vectorizer).

Types / choices

ChoiceWhat it doesWhen to use
Stopword lists (sklearn / NLTK)Removes a fixed English listShort titles, bag-of-words, classic NLP baselines
Keep punctuation/emojisPreserves style signalsSentiment, social media tone
Stemming / lemmatizationMaps running/runs → rootLong documents, vocabulary reduction
Domain stopwordsCustom ignore listLegal, medical, support tickets

General example

Raw:     "The Songs of Adelaide & Abullah!"
Lower:   "the songs of adelaide & abullah!"
Letters: "the songs of adelaide   abullah "
Tokens:  the, songs, of, adelaide, abullah
Clean:   "songs adelaide abullah"

In our project

Notebook: notebooks/02_text_cleaning.ipynb
Column created: name_clean
Saved to: data/interim/ks_text_cleaned.csv

Kickstarter 2018 has no long description field, so the text modality is the short campaign name. Cleaning still matters: titles are short, so every wasted token hurts more than in long articles.

Where else this applies

  • Spam classification on email subjects
  • Support-ticket tagging from customer messages
  • News topic classification
  • Resume / job-description matching
  • Product review sentiment baselines

Key takeaway

Cleaning is not “making text pretty.” It is controlling what the model is allowed to count.

2. Train/test split & data leakage

What it is

A train/test split separates data you learn from (train) and data you evaluate on (test). Leakage means the model saw information it would not have at prediction time — either from the future, from the label itself, or from statistics computed using the test rows.

Why we need it

Without a clean split, scores look great and fail in production. Leakage is the most common silent killer of student and industry demos.

How it works

  • Random split: shuffle then cut (e.g. 80/20).
  • Stratified split: keep class proportions similar in both sets (important for imbalanced labels).
  • Time-based split: train on past, test on future (sales, finance, clicks).
Fitting rule: any transformer that learns from data (TF-IDF vocabulary, StandardScaler mean/std, OneHotEncoder categories) must be fit on train only, then transform on test.

Types of leakage (practical)

TypeExampleFix
Target leakageUsing backers to predict funding successDrop outcome columns
Fit leakageFitting TF-IDF on all rows including testFit on train only
Duplicate leakageSame ID in train and testDeduplicate before split
Pipeline leakageScaling with global mean including testUse Pipeline + train fit

General example

# Wrong: learn vocab from everyone, then "evaluate"
vectorizer.fit(all_texts)
X = vectorizer.transform(all_texts)

# Right
X_train = vectorizer.fit_transform(train_texts)
X_test  = vectorizer.transform(test_texts)

In our project

  • Phase 1 dropped leakage columns: pledged, backers, usd pledged, usd_pledged_real.
  • Phase 3 used stratified 80/20 split (random_state=42) before TF-IDF.
  • IDs saved in data/processed/split_ids.csv so later tabular steps stay aligned.

Where else this applies

  • Credit risk scoring (never use post-default fields)
  • Churn prediction (exclude cancellation timestamps as features)
  • Medical diagnosis models (exclude lab values only available after decision)
  • Forecasting demand with a time-aware split

3. TF-IDF (Term Frequency–Inverse Document Frequency)

What it is

TF-IDF converts text into numbers. Each document becomes a vector over a vocabulary. A word scores high if it appears often in this document but rarely across the whole corpus.

Why we need it

Classifiers cannot read strings. Raw counts treat “project” (everywhere) the same as “ballet” (rare and informative). TF-IDF down-weights common words and up-weights distinctive words.

How it works

Term Frequency (TF) — how often term t appears in document d.

TF(t, d) = count(t in d) / total tokens in d   (one common form)

Inverse Document Frequency (IDF) — how rare term t is across documents.

IDF(t) = log( (1 + N) / (1 + df(t)) ) + 1   (sklearn-style smoothing)

TF-IDF weight

TF-IDF(t, d) = TF(t, d) × IDF(t)

Sklearn then often L2-normalizes each document vector so long vs short documents are comparable.

Types / knobs

KnobMeaningOur choice
max_featuresKeep only top N terms by frequency across corpus2500 (handbook limit)
ngram_rangeUnigrams vs bigrams ("new york")(1, 1) for Phase 3 simplicity
min_df / max_dfIgnore ultra-rare / ultra-common termsmin_df=2
Binary TFPresence/absence instead of countsNot used (default counts)

General example

Corpus of 3 titles:

  1. “music album release”
  2. “music festival poster”
  3. “ballet dance show”

music appears in 2/3 docs → lower IDF.
ballet appears in 1/3 → higher IDF.
In doc 3, ballet gets a stronger weight than a repeated common word would.

In our project

Notebook: notebooks/03_tfidf.ipynb
Matrices: X_text_train.npz, X_text_test.npz shape [N × 2500], density ≈ 0.1%. 

vectorizer = TfidfVectorizer(max_features=2500, ngram_range=(1, 1), min_df=2)
X_train = vectorizer.fit_transform(train_df["name_clean"])
X_test  = vectorizer.transform(test_df["name_clean"])

Where else this applies

  • Search ranking and keyword retrieval baselines
  • Document classification (news, tickets, emails)
  • Duplicate question detection (with cosine similarity)
  • Simple content recommendation
  • As features feeding logistic regression / linear SVM
Learning tip: TF-IDF is still a “bag of words.” Word order is mostly ignored unless you use n-grams. Transformers understand context better, but TF-IDF remains a strong, interpretable baseline and is required in this project.

4. Sparse vs dense matrices

What it is

A dense matrix stores every value (including zeros). A sparse matrix stores mostly the non-zero values and their positions.

Why we need it

TF-IDF vectors are almost all zeros: each title activates maybe 3–8 tokens out of 2500. Storing that densely wastes RAM and CPU. Sparse formats keep high-dimensional text affordable.

How it works (intuition)

Dense row:  [0, 0, 0.41, 0, 0, 0, 0.22, 0, ... 0]   # 2500 numbers stored
Sparse row: store only (index=2 → 0.41), (index=6 → 0.22)

Common SciPy formats: CSR / CSC (efficient math), COO (easy construction). Sklearn TF-IDF returns sparse CSR by default.

Types

FormatBest for
CSR (Compressed Sparse Row)Row slicing, matrix × vector, sklearn estimators
CSCColumn slicing
COOBuilding matrices from coordinate triples
Dense ndarraySmall tabular matrices after one-hot may still be manageable

In our project

Text features are sparse (.npz files). Tabular features will be denser. Direct np.hstack on mixed types is the wrong tool; we will use scipy.sparse.hstack (Phase 5–6).

Where else this applies

  • One-hot encodings with huge category spaces
  • Recommender user–item matrices
  • Graph adjacency matrices
  • Genomics / bag-of-k-mers features

5. Categorical encoding & numeric scaling

Phase 4 · implemented in notebooks/04_tabular_preprocess.ipynb.

What it is

Encoding turns categories (country, currency, category) into numbers. Scaling puts continuous numbers on a comparable scale so large-magnitude features do not dominate distance- or gradient-based linear models.

Why we need it

  • Logistic regression expects numeric inputs.
  • usd_goal_real can be thousands; one-hot flags are 0/1. Without scaling, goal magnitude can overwhelm.
  • After fusion with TF-IDF (already normalized), tabular scaling keeps modalities balanced.

How encoding works

One-hot encoding

Each category level becomes its own 0/1 column.

country: US → [1, 0, 0]
country: GB → [0, 1, 0]
country: CA → [0, 0, 1]

Other encoding types

TypeIdeaWatch-out
One-hotIndependent binary columnsMany levels → many columns
OrdinalMap to ranked integersOnly if order is real
Target / mean encodingReplace category by average labelEasy leakage if done wrong
Hashing trickHash categories into fixed binsCollisions; less interpretable

How scaling works

ScalerFormula ideaUse when
StandardScaler(x − mean) / stdDefault for linear models
MinMaxScalerstretch to [0, 1]Bounded neural-net inputs
RobustScaleruses median/IQRHeavy outliers
Log transformlog1p(x)Right-skewed money/counts (often before scaling)

General example

goal_usd = 15000
duration = 30

After StandardScaler (fit on train):
goal_scaled ≈ 0.42
duration_scaled ≈ -0.10

In our project

  • Numeric: usd_goal_real, duration_days → StandardScaler
  • Categorical: category, main_category, currency, country → OneHotEncoder
  • Fit on the same train IDs as TF-IDF; artifacts in X_tab_*.npz
  • Notes: docs/tabular.md

Where else this applies

  • Any tabular ML pipeline (pricing, churn, fraud)
  • Mixing sensors of different units in industrial IoT models
  • Linear models and k-NN (distance sensitive); tree models often need less scaling

6. Multi-modal feature fusion (sparse.hstack)

Phases 5–6 concept (core of this project).

What it is

Feature fusion means combining different feature families into one model input. Here: sparse text TF-IDF + dense/sparse tabular features → one wide matrix.

Why we need it

Titles capture wording/theme. Tabular fields capture budget, geography, category, duration. Either alone is weaker than both together for funding prediction.

How it works

Xfused = [ Xtfidf sparse | Xtabular ]

Horizontally stack columns. Row i in text must be the same campaign as row i in tabular (same ID order / same split). 

from scipy.sparse import hstack, csr_matrix

X_train_fused = hstack([X_text_train, csr_matrix(X_tab_train)])
X_test_fused  = hstack([X_text_test,  csr_matrix(X_tab_test)])

Types of fusion

TypeIdeaNotes
Early fusionConcatenate features, one modelWhat we do (hstack + logistic regression)
Late fusionTrain separate models, blend predictionsUseful when modalities disagree
Intermediate / learned fusionNeural nets merge embeddingsMore flexible, less interpretable

Why not simple numpy concatenate?

Text is sparse; tabular is dense. Naive dense concatenation explodes memory. scipy.sparse.hstack keeps the result sparse-friendly.

Where else this applies

  • Lead scoring: CRM fields + email text
  • Insurance: claim forms (text) + policy numbers
  • Marketplaces: listing description + price/category
  • Healthcare: clinical notes + vital signs
  • Content moderation: post text + account metadata

7. Logistic regression (binary classification)

Phase 7 model.

What it is

A linear model for probabilities. It learns a weight per feature, combines them into a score, then squeezes that score through a sigmoid into a probability between 0 and 1.

Why we need it

  • Matches our binary target (successful vs failed).
  • Works well with high-dimensional sparse TF-IDF.
  • Coefficients are readable — important for this project’s feature-weight analysis.

How it works

z = w₀ + w₁x₁ + w₂x₂ + … + wₚxₚ P(y=1 | x) = σ(z) = 1 / (1 + e−z)

Training usually minimizes log-loss (cross-entropy): penalize confident wrong probabilities, with an optional regularization term on weights.

Decision threshold

Default: predict class 1 if probability ≥ 0.5. You can move the threshold to trade precision vs recall (important when false positives and false negatives have different business costs).

Where else this applies

  • Click-through prediction baselines
  • Medical risk scores
  • Fraud / spam flags
  • Any “yes/no” problem where you want calibrated probabilities and explainable weights

8. Regularization: L1 (Lasso), L2 (Ridge), ElasticNet

Critical for high-dimensional text + tabular fusion.

What it is

Regularization adds a penalty on weight size while training. It stops the model from relying too hard on noisy features — especially when you have thousands of TF-IDF columns.

Why we need it in this project

After fusion, text features outnumber tabular features (~2500 vs maybe dozens). Without regularization, sparse title tokens can dominate and overfit rare words. L2 keeps weights small; L1 can zero out weak tokens; ElasticNet mixes both.

How each type works

NamePenaltyEffect on weightsGood for
L2 / Ridge Σ w² Shrinks weights smoothly, rarely to exact zero Correlated features; stable sparse text models (our Phase 7 start)
L1 / Lasso Σ |w| Can set many weights exactly to 0 (feature selection) Finding a small set of influential tokens
ElasticNet mix of L1 + L2 Sparse + stable When you want selection without Lasso instability

Strength control (sklearn mental model)

In LogisticRegression, C is inverse regularization strength:

  • Smaller C → stronger penalty → simpler model
  • Larger C → weaker penalty → fits train data more aggressively
# L2 (default idea)
LogisticRegression(penalty="l2", C=1.0, solver="saga")

# L1
LogisticRegression(penalty="l1", C=0.5, solver="saga")

# ElasticNet
LogisticRegression(penalty="elasticnet", l1_ratio=0.5, C=1.0, solver="saga")

General intuition example

Imagine two title tokens that appear once and coincide with success by luck. Without regularization, their weights can explode. With L2, they shrink. With L1, they may vanish entirely if they are not consistently useful.

Where else this applies

  • Genomics (p ≫ n feature regimes)
  • Marketing mix models with many correlated channels
  • Any linear model on wide one-hot / TF-IDF spaces

9. Precision, Recall, F1, and Precision–Recall curves

Phase 8 evaluation. Needed because our classes are ~60/40, not perfectly balanced.

Confusion matrix ingredients

TermMeaning
TPPredicted successful, actually successful
FPPredicted successful, actually failed
TNPredicted failed, actually failed
FNPredicted failed, actually successful

Core metrics

Precision = TP / (TP + FP)    “Of campaigns we marked successful, how many truly were?” Recall = TP / (TP + FN)    “Of all true successes, how many did we catch?” F1 = 2 · (Precision · Recall) / (Precision + Recall)    harmonic balance Accuracy = (TP + TN) / all    easy to misuse with imbalance

Why not only accuracy?

If 90% of rows are “failed,” predicting always-failed gets 90% accuracy and zero business value. Precision/Recall/F1 force you to look at the positive class behavior.

Precision–Recall curve

Sweep the probability threshold from high → low. Plot Precision vs Recall at each threshold. Useful when the positive class is rarer or when you care about ranking quality of “likely to fund” campaigns. Average Precision (AP) summarizes the curve into one score.

Business reading (Kickstarter-like)

  • High precision: fewer false “will fund” calls (good if you allocate scarce outreach budget).
  • High recall: miss fewer true successes (good if missing a winner is costly).

Where else this applies

  • Fraud detection (recall often critical)
  • Cancer screening (tradeoffs are life-critical)
  • Search ranking quality
  • Lead scoring dashboards

10. Feature coefficients & interpretability

Phases 7–8 deliverable: top positive/negative text tokens vs tabular weights.

What it is

In logistic regression, each feature has a coefficient w. Sign and magnitude tell you how that feature pushes the log-odds of success.

How to read them

  • Positive coefficient: higher feature value → higher chance of success (all else equal)
  • Negative coefficient: higher feature value → lower chance of success
  • Near zero: weak/noisy contribution under current regularization
Coefficients are comparable more cleanly when inputs are scaled. For one-hot flags, a coefficient is the effect of that category versus the dropped reference level. Correlation ≠ causation — treat them as model explanations, not proven business laws.

In our project (planned analysis)

  1. Train regularized logistic regression on fused matrix.
  2. Split coefficients into text-token block vs tabular block.
  3. Plot top 15 positive and top 15 negative text tokens.
  4. Plot strongest tabular feature weights beside them.

Where else this applies

  • Credit decision explanations
  • Policy / compliance model audits
  • Marketing drivers (“which words correlate with conversion?”)
  • Healthcare risk factor summaries
